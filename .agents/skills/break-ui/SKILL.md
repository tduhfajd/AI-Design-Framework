# Проверка интерфейса на крайних данных

Исследуй данные, которые действительно допускает продукт, и проверь их через
тот же компонент. Результат — воспроизводимый набор, наблюдения и границы вывода,
а при запрошенном исправлении — также изменение и повторная проверка.

## Режим и область записи

Сначала прочитай запрос, правила проекта, затронутый компонент, источник данных
и известные ограничения схемы. Каталог навыка не является целевым сайтом.

- **Проверка / review** — отчёт и доказательства; исходники, конфигурация,
  данные и зависимости продукта неизменны. Для смены данных используй существующий
  тестовый вход либо изолированный стенд в разрешённом каталоге вне исходников.
  Копирование для проверки допустимо в пределах запроса; копию явно отличай
  от целевого сайта. Если запись даже такой копии запрещена, сохрани доступный
  анализ и непроверенную часть. Не вставляй dev-toggle в целевой сайт ради аудита.
- **Стенд без исправления** — создай запрошенные фикстуры и переключатель только
  в разрешённом тестовом месте. Исследуемый компонент и его CSS сохрани;
  проблемы не исправляй как побочный эффект подготовки стенда.
- **Исправление / implementation** — при явном запросе исправь доказанные
  проблемы в разрешённых файлах и повтори проверки. Уже разрешённое исправление
  не требует нового вопроса. Неоднозначное продуктовое решение вынеси отдельно.

Неизвестный режим трактуй как проверку, а не разрешение менять продукт.
Границы родительского review/implementation действуют и внутри специализации.

## Работа

1. **Карта полей.** Перечисли отображаемые значения, их источники, тип,
   обязательность и реальные пределы. Предел не найден — «неизвестен», а не
   утверждение о неограниченной базе. Учитывай подписи, количество строк,
   статусы, медиа и действия, а не только основной заголовок.
2. **Наборы.** По [каталогу](references/catalog.md) выбери применимые крайние
   значения. Сохрани обычный набор, смешанный худший набор, Empty и One.
   Большой набор обоснуй схемой, пагинацией и задачей; тысяча строк не обязательна
   для компонента с жёстким пределом. Неприменимое запиши с причиной.
3. **Граница данных.** Подавай набор через props, fixture, mock, параметр
   или другой действующий вход. Не изменяй CSS/разметку, чтобы искусственно
   получить поломку. В копии используй тот же компонент и стили, запиши изменения
   окружения. Переключатель обычного/крайнего/пустого/одиночного набора оставь
   только в тестовом стенде; он не входит в production-сборку.
4. **Просмотр.** Проверь реальную ширину контейнера, узкую и широкую компоновку,
   обычно включая 320 px. Проверь увеличение текста или zoom 200%; зафиксируй
   точный способ — изменение root font-size не тождественно browser zoom.
   Dark/RTL испытывай при поддержке продуктом, не добавляй их ради списка.
   Открой и просмотри снимки обычного и крайних состояний, проверь доступность
   действий, переносы, переполнение, фокус и применимые состояния.
5. **Вывод.** Для замечания сохрани набор и значение, версию, размер,
   наблюдение, доказательство, последствие и предложение. Чтение CSS даёт риск,
   а не просмотренный дефект. Без браузера визуальная часть остаётся открытой.
   Вкусовое предложение отделяй от недоступного действия и неверных данных.
6. **После исправления.** Повтори крайние и обычный наборы, затронутый путь
   и размеры. Закрой замечание только по новому доказательству. Фикстуры сохрани
   для воспроизведения в тестовом месте, если пользователь не требует удалить их.

При Playwright используй bundled Chromium с отдельным профилем. Существующую
пользовательскую сессию Chrome подключай только явно запрошенным Chrome plugin;
не запускай обычный Chrome через Playwright. Закрывай собственные ресурсы.
Синтетические данные не отправляй во внешние системы.

## Результат

Дополни существующий REVIEW/IMPLEMENTATION или сохрани отдельный короткий отчёт:
режим и пути записи; версия и карта полей; наборы и их происхождение; проверки
с состояниями «пройдено / не пройдено / не проверено / неприменимо»; замечания
с доказательствами; что выдержало проверку; изменения или их отсутствие;
неоднозначные решения и следующий допустимый шаг.

BU-01: данные обоснованы и введены через действующую границу компонента.
BU-02: режим, область записи и неизменность защищённых файлов подтверждены.
BU-03: выводы отделяют наблюдение от предположения и ограничены набором/средой.
BU-04: запрошенные исправления повторно проверены и на обычных данных.
Для проверки без исправления BU-04 неприменим с причиной.

Отчёт может быть готов при открытых дефектах. Недоступный просмотр означает
частичную проверку, а не одобрение интерфейса. Выбор оформления и публикация
не следуют из stress-теста. [Происхождение адаптации](SOURCE.md).
